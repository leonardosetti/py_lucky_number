## Summary

Implementar a versão 0.1-beta do Lucky Number, unificando todos os 21 specs em uma única base de código modular, segura e testável. Partindo do código existente (94 testes, 91.74% cobertura, geração de combinações, precificação, cliente Caixa API), o plano evolui o projeto para:

1. **10 coletores de dados** (specs 007–017) baixando planilhas XLSX da CEF com Polars, armazenando em JSON (orjson) e PostgreSQL (asyncpg), com scheduler Celery Beat
2. **Banco de dados relacional** PostgreSQL 16+ com SQLAlchemy 2.0 + Alembic — tabela por jogo (`loterias_resultados_{jogo}`)
3. **Sistema modular de features** com toggle ativar/desativar via admin (spec 002)
4. **Gestão de usuários, roles e permissões** hierárquica com JWT + bcrypt (spec 003)
5. **Promessas de aposta** com snapshot, FIFO, compartilhamento HMAC (spec 001)
6. **Notificações do sistema** + dashboard de tracking com filtros (spec 003)
7. **4 ambientes isolados** com Docker Compose profiles e volumes nomeados (spec 006)
8. **Ferramenta de backup em Go** (pg_dump + AES-256-GCM + S3) (spec 005)
9. **Stack assíncrona obrigatória**: FastAPI + HTTPX + Polars + asyncpg + orjson + Celery/Redis
10. **Web Frontend** responsivo (spec 020): WCAG 2.2 AA, data-testid, mobile-first
11. **Mobile App** Android + iOS (spec 021): biometria, offline, push, swipe
10. **OWASP/CWE** compliance: prepared statements, Pydantic validation, logs sanitizados, containers não-root

## Architecture Decisions

### Why 10 separate database tables (one per game)?

Each lottery has unique columns (different number of balls, prize brackets, special fields like "Time Coração" or "Trevos"). A single generic table would require:
- Dozens of nullable columns (inefficient)
- Complex mapping logic per game
- Loss of column name fidelity with source spreadsheet

**Decision**: `loterias_resultados_{jogo}` per game. Total: 10 tables.

### Why Polars instead of Pandas?

| Criteria | Polars | Pandas |
|---|---|---|
| Memory efficiency | ✅ Lazy/streaming, no copy | ❌ Loads entire file in memory |
| Performance | ✅ 3–5x faster on XLSX | ❌ Slower |
| API | ✅ Polars-native `.str` API | ❌ Complex string handling |
| Async compatibility | ✅ Works with asyncpg | ❌ Sync-only |

### Why pgBackRest + Go backup-tool (two layers)?

Backups têm dois propósitos distintos que exigem ferramentas diferentes:

| Critério | pgBackRest (físico) | Go tool (lógico) |
|---|---|---|
| **Tipo** | WAL archiving + snapshot | pg_dump custom format |
| **RPO** | Minutos (WAL contínuo) | 24h (agendado) |
| **Restore** | Banco completo point-in-time | Tabelas/seleções específicas |
| **Uso primário** | Disaster recovery | Mirror, dev/QA, exportação seletiva |
| **Spec** | 004 (FR-035) | 005 |

**Decisão**: Ambos são necessários e complementares.

### Why BaseLotteryCollector?

All 10 collectors share identical behavior (download → parse → compare → append → insert). The abstract base class enforces:
- Zero duplicated code
- Single retry/error-handling logic
- Single Prometheus metric registration pattern
- Easy addition of new games (1 subclass + 1 Celery Beat entry)

   ```python
   class BaseLotteryCollector(ABC):
       URL: str                      # URL da planilha CEF
       COLUMNS: list[str]            # Nomes das colunas
       TABLE_NAME: str               # loterias_resultados_{jogo}
       JSON_PATH: str                # ./data/{jogo}.json
       GAME_LABEL: str               # Prometheus label
       DRAW_DAYS: list[int]          # Dias da semana (0=seg, 6=dom)
       DRAW_HOUR: int = 21           # Horário BRT do sorteio
       EXTRA_CHECK_HOUR: int = 22    # 1h após sorteio

       async def download_excel(self) -> bytes
       def parse_to_dataframe(self, content: bytes) -> DataFrame
       def get_last_contest_from_json(self) -> int
       def filter_new_contests(self, df, last_id) -> DataFrame
   async def append_to_json(self, new_records: list[dict])
   async def bulk_insert_to_db(self, records: list[dict])
   # Hash O(1) já incluso na tabela loterias_resultados_{jogo} via constraint UNIQUE em hash_combinacao
   ```

## Complexity Tracking

| Violação | Por que é necessária | Alternativa rejeitada |
|---|---|---|
| 10 tabelas separadas (1 por jogo) | Cada jogo tem colunas únicas (bolas, trevos, time coração, colunas) | Tabela genérica exigiria dezenas de colunas nullable |
| `combinacoes_salvas` com hash UNIQUE | Impede combinações duplicadas no histórico do usuário | Sem hash, duas gerações poderiam produzir a mesma combinação |
| Frontend + Mobile como fases separadas | Web e Mobile compartilham API mas têm stacks distintas | Unificar atrasaria ambos (web mais simples, mobile mais complexo) |
| Biometria + Keychain/Keystore | Segurança mobile (CWE-522) | Apenas senha seria menos seguro |
| BaseLotteryCollector abstrato | 10 coletores com 90%+ de lógica compartilhada | Copiar código 10x viola DRY |
| Go separado para backup lógico | Performance I/O + static binary sem runtime | Python adicionaria dependências e 2x+ tempo |
| pgBackRest para backup físico | WAL archiving contínuo, RPO de minutos | Apenas pg_dump teria RPO de 24h |
| Celery + Redis | Scheduler complexo com 10+ tarefas periódicas + janelas críticas | Cron insuficiente para lógicas condicionais |
| Prometheus por game + Loki | Observabilidade em 10 coletores simultâneos | Logs textuais impossíveis de correlacionar |
